# 10c8:0100 inferred_stretch_setup
Status: understood · Cluster: 32-bit bitmap helpers · Convention: 32-bit near/far code in a USE32 segment (Ghidra decodes it as 16-bit; read with `ne_segments.py dis --use32`)

**Purpose (inferred):** Check the arguments of a stretch copy, compute the source and destination positions and strides and the two stretch ratios, and pick the routine that will do the work.
**Inputs:** The caller's frame (set up by `10c8:0040`): flags word (bit 0 mirrors horizontally), source and destination rectangle sizes, source and destination picture headers and pixel pointers.
**Outputs / state written:** Fails (`10c8:00fe`, carry set) if any of the four sizes is 0, the source and destination bit depths differ or the depth is not 8, 16, 24 or 32. Otherwise it computes the byte offsets of the first source and destination pixels (a negative destination height flips the copy), the row gaps, calls `10c8:0073` for the horizontal ratio (index added to the table at `10c8:0000` to choose the row routine, stored in the frame) and for the vertical ratio, stores both ratios in the frame and returns with carry clear.
**Calls:** `10c8:0073`, `10c8:00fe`.
**Yields / blocks / timing:** none
**Edge cases:** Only two row routines are in the table: `10c8:0223` for shrinking horizontal ratios and `10c8:039e` for the others; they are not in the ledger and not read. Some of the stride arithmetic looks overwritten by later stores (the frame words at -0x24 and -0x34 take the rectangle width), so the layout of the frame is not settled.
**Evidence:** `ne_segments.py dis 10c8:0100 0x123 --use32`; caller `10c8:0040`.
**Port:** none yet
**Validation:** none yet
**Open questions:** The frame layout; the two row routines; whether the keyed (RLE) source format of `10b8:02b2` is what they read.
